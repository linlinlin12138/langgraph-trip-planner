# 评测方法

一条命令跑完：

```bash
make eval ARGS="--split dev --repeats 3"          # 默认 mock，无需 key
```

产物在 `evals/runs/<name>/`（mock，不进 git）或 `evals/results/<name>/`（真实模型，进 git：生成要花钱，换 Judge 重新打分也要用到保存的行程，跑完记得提交）：`meta.json`（模型、commit、数据集、种子）、`records.jsonl`（每条样本 × 系统 × 第几次运行的明细）、`summary.json`、`report.md`。用同一个 `--name` 重跑时会跳过已完成的记录，可以断点续跑。遇到不可恢复的服务端错误（Gemini 月度消费上限、OpenAI 额度用完、Anthropic 余额不足、key 无效或无权限）时，运行会立刻停下：排队的任务取消，出错的那条不写入记录，以退出码 2 结束；处理好账单或 key 之后，原命令续跑即可。普通的每分钟限流由 SDK 自动退避，不会触发停止。其他报错（504、断网）会记成错误记录，用 `--retry-errors` 重跑。比较两次运行：

```bash
make eval-compare A=evals/runs/<a> B=evals/runs/<b>
```

## 数据集

`evals/datasets/{dev,test}.jsonl`，由 `python -m trip_agents.evals.dataset` 生成（seed=42，共 200 条，dev 60 / test 140）。

1. **先采样结构化约束，再改写成自然语言。** 每条样本保存生成它的约束（`gold`），用作标准答案。改写有两种方式：`template` 是确定性模板，mock 抽取器能 100% 还原；`llm` 是让模型改写，更口语化，需要 key，会产生费用。
2. **难度在生成时确定**（简单 35% / 中等 40% / 困难 25%），看约束数量和预算松紧，与模型表现无关：

   | 难度 | 天数 | 人数 | 饮食限制 | 必去景点 | 兴趣 | 预算 |
   |---|---|---|---|---|---|---|
   | 简单 | 1–3 | 1–2 | 0 | 0 | 0–1 | 典型花费的 1.6–2.2× |
   | 中等 | 2–4 | 1–3 | 0–1 | 0–1 | 1–2 | 典型花费的 1.15–1.5× |
   | 困难 | 3–5 | 2–4 | 1–2 | 1–2 | 2–3 | **最低可行花费**的 1.1–1.6× |

   人数的说法必须唯一确定：2 人写成“我和女朋友”“我和一个朋友”“我们两个人”，不用“我和朋友”（可以是一个朋友，也可以是几个；Gemini 试跑里被理解成 1 人，标准答案却是 2 人）。

   饮食限制只有“不吃辣”“不吃海鲜”两种，都能从餐厅菜系推出来（清真、素食需要逐店认证，开放数据里没有）。必去景点只从每城 15 个手工整理的名胜里抽。困难样本的区分度主要来自紧预算：贵一点的酒店或餐厅就会超支，必须靠预算核算和回退重排。

3. **不可行样本**（约 6%，12 条）：预算是“全目录最低可行花费”的 0.4–0.7 倍。这个下界用整个城市目录计算，公式与 Budget Agent 相同。简单、中等样本的预算至少是下界的 1.25 倍。
4. **期望工具**：天气、景点、餐厅三类必查；多日行程再加酒店和路线。
5. **划分**：按难度 × 可行性分层；test 集只用于最终评测。

## 评判：不相信系统的自我报告

系统内部用**自己检索到的结果**做校验。评测时，最终行程会重新对照**完整城市目录**和**标准答案约束**检查一遍（`evals/world.py`）：

- 引用既可以是 id，也可以是名称（没有检索的系统只知道名称），先统一解析成 id；解析不了的算作**实体幻觉**。
- 用的是标准答案里的约束，而不是系统抽取出来的。因此抽取错误也会体现在结果里。

## 指标

| 类别 | 指标 | 定义 |
|---|---|---|
| 结果 | 结构正确率 | 天数正确且每天至少有一项活动 |
| | 硬约束通过率 | **只统计可行样本**：日期、时间冲突、开放时间、引用、饮食、必去景点、预算全部通过 |
| | 实体幻觉率 | 无法解析的引用数 ÷ 引用总数 |
| | 需求抽取准确率 | 7 个硬约束字段的平均准确率 |
| | 不可行识别率 / 误报率 | 不可行样本中被标记出来的比例 / 可行样本中被误标的比例 |
| | 模型估价偏差 | （模型填的 `est_cost` 之和 − 目录价格之和）÷ 目录价格之和，只统计能解析到目录的景点和餐饮。预算判定**不用**模型估价，见下文 |
| | 少报超过 10% 的计划数 | 模型估价比目录价格低 10% 以上的计划数 |
| | 按模型估价判预算会改变结论的计划数 | 如果相信模型估价，超预算结论会翻转的计划数，用来量化“少报就能过预算”这个漏洞原本的影响 |
| | 合格计划质量分 | Judge 给出丰富度、偏好符合度、合理性三个维度（各 0–100），由代码加权（默认 0.3 / 0.4 / 0.3）。**只对硬约束全部通过的计划打分**，报告写成“79.0（n=5）”，n 为参与评分的计划数；没有计划通过时为 N/A。规则和原因见下文 |
| 过程 | 工具精确率 / 召回率 | 实际用到的工具集合与期望工具集合比较，按样本取平均 |
| | 无效调用率 / 重复调用率 | 汇总所有调用后计算 |
| | 步数、回退次数、解析失败次数 | 取平均 |
| 效率 | token、估算费用、端到端耗时的均值和 P95、各节点耗时 | 单价表里没有的模型，费用显示为 n/a，不做估算 |
| 稳定性 | 结果一致率、景点集合 Jaccard、Judge 分标准差 | 同一样本多次运行之间比较，需要 `--repeats ≥ 2` |

Gemini 的推理强度默认为 `low`（`LLM_THINKING_LEVEL`），记录在 `meta.json` 的 `thinking_level` 和报告抬头里。5 条 dev 样本的对比：完整系统每条 $0.085 → $0.035、348 秒 → 51 秒，合格率 80% → 100%（默认推理下一条 5 天行程 504 超时）；去掉回退的合格率从 80% 降到 40%，低推理下模型更依赖规则校验和回退。

**花费以目录价格为准**：预算核算和所有规则判定都用 `graph/costs.py` 计算（景点门票 × 人数、餐厅人均 × 人数、休息 0；交通和无法解析到目录的实体用模型估价）。评测时 `evaluate_plan` 先把计划里的 `est_cost` 改写成这些值再核算，所以模型少报估价不能让计划通过预算检查。原因和影响见 DESIGN §9。

多次运行时，每个指标先按每一轮算出来，再报告各轮的**均值 ± 标准差**。每轮的种子是 `seed + rep`；目前只有 OpenAI 支持传入 seed。

## 必去景点名称怎么算对

用户和模型写的景点名常常和目录里的不一样（“故宫”vs“故宫博物院”，“兵马俑”vs“秦始皇帝陵博物院(兵马俑)”）。v5 起，**规则校验**（计划里有没有安排必去景点）和**抽取准确率**（系统抽出的必去景点对不对）用同一条规则（`validation/names.py` 的 `same_place`）：

1. 先把名字规整成几种写法：去掉城市前缀（北京 / 上海 / 杭州 / 成都 / 西安，可带“市”）、去掉括号部分后的名字；再加上括号里的别名本身（目录用括号写别名）。
2. 两个名字的任意两种写法之间，只要一个**连续包含**另一个，就算同一个地方。少于两个字的写法只认完全相同。
3. 抽取准确率：抽出的必去景点和标准答案**一一对应**（数量相同，每个标准答案都能匹配到抽出的某一个，反之亦然）才算对。

| 写法 | 目录名 | 算对吗 | 原因 |
|---|---|---|---|
| 故宫 | 故宫博物院 | 对 | 简称是全称的连续一部分 |
| 成都大熊猫繁育研究基地 | 大熊猫繁育研究基地 | 对 | 去掉城市前缀后相同 |
| 兵马俑 | 秦始皇帝陵博物院(兵马俑) | 对 | 括号里的别名 |
| 熊猫基地 | 大熊猫繁育研究基地 | **不对** | 俗称既不是连续子串，也不是目录里写的别名 |
| 武侯祠 | 杜甫草堂 | 不对 | 不同地方 |

也就是说：简称只要是全称里连续的一段就算对；俗称只有目录在括号里收录了它才算对，其余俗称都不算。这条规则偏宽，极少数情况下可能把两个名字相近的地方当成同一个；目前每个城市只有约 45 个景点，没有发现这种冲突。v5 之前，抽取准确率要求名字逐字相同，规则校验只做“去括号后包含”。

## 挑战集：模板措辞之外的说法

模板生成的请求措辞固定，系统可能只是适应了模板。挑战集用更难的说法重写一部分 test 样本，标准答案不变：

1. **选样**：`python -m trip_agents.evals.challenge select` 从 test 集按难度分层挑 36 条（简单 / 中等 / 困难各 12 条，其中 3 条不可行：中等 2、困难 1），seed 固定，id 写入 `evals/datasets/challenge/ids.json`。
2. **改写**：`challenge rewrite` 用 Anthropic 模型（默认 claude-sonnet-5-5，与被测的 Gemini 不同家）改写。和 `evals.rewrite` 不同，这里**不做回检**，也不要求必去景点逐字出现：鼓励简称和俗称、中文数字和口语预算、能唯一确定的相对日期、间接的人数说法、信息打乱。改写结果写入 `review.csv`，**每一条都由人工检查**（ok / edit / drop），`challenge apply-review` 生成最终的 `test_challenge.jsonl`。
3. **评测**：只对挑战集跑 `full` 和 `baseline_catalog`（`--dataset evals/datasets/challenge/test_challenge.jsonl`）。模板版的结果直接复用 `gemini_test_v1` 中相同 id 的记录，不重跑。
4. **报告**：`challenge compare <模板运行> <挑战运行>` 对同一批 id 比较硬约束通过率（按难度）和逐字段的抽取准确率，列出挑战版每一处抽取错误（样本、字段、标准答案、抽取结果、模板版是否抽对、请求原文），以及硬约束结论不同的样本。

### 挑战集结果（`gemini_challenge_v1`，36 条，Gemini 3.8 Flash，推理强度 low，生成花费 $2.05）

改写模型 claude-sonnet-5-5，36 条全部人工检查（5 条按建议修改，其余通过）。模板版取自 `gemini_test_v1` 相同 id 的记录。完整对比见 [`compare.md`](../evals/results/gemini_challenge_v1/compare.md)。

| | 模板版 | 挑战版 |
|---|---|---|
| full：硬约束通过率（可行 33 条） | 87.9% | 84.8% |
| 　easy / medium / hard | 100% / 100% / 63.6% | 100% / 100% / 54.5% |
| full：抽取全部正确的样本 | 36/36 | 35/36 |
| baseline_catalog：硬约束通过率 | 63.6% | 57.6% |

- **full 的需求抽取对改写很稳**：日期（含“下个月 5 号”“这个月 24 号”“二十天后”）、“三天两夜 / 待四晚”、“带上爸妈 / 一家四口”、“两千五 / 一人两千二百五”、“对海鲜过敏 / 一点辣都吃不了”全部抽对。唯一的抽取错误是 s193 的“国博”：既不是“中国国家博物馆”的连续子串，也不是目录收录的别名，按规则算错；运行时按“国博”检索不到这个景点，于是没排进行程，这条样本因此不合格。简称“故宫”算对。
- **硬约束通过率的变化在噪声范围内**：full 在 hard 上有两条结论翻转，方向相反（s170 由不过变过、s183 由过变不过，都是超预算），只有 s193 的失败可以归因于改写。两边各只跑了 1 次，1–2 条的差异不能当作结论。
- **baseline_catalog 下降 6 个百分点**，多出来的失败主要是闭馆，也是两个方向都有。
- **局限**：目录里没有收录俗称，像“国博”“熊猫基地”这样的说法系统找不到。可以从 Wikidata 的别名（aliases）补一张别名表，用在检索和名称匹配上。

### 稳定性（`gemini_test_stability`）

从 test 集按“难度 × 是否可行”分层抽 40 条（seed 固定，名单 `ids.json`），full 跑 3 次：第 1 次取自 `gemini_test_v1`（只读复制），第 2、3 次新跑（seed 依次为 43、44，花费 $2.76），新跑的合格计划用 gpt-6.1-sol 打分，第 1 次保留原分数。报告见 [`evals/results/gemini_test_stability/report.md`](../evals/results/gemini_test_stability/report.md)。

| 指标 | 结果 |
|---|---|
| 硬约束通过率（可行样本，3 次的均值 ± 标准差） | 91.0% ± 3.1 |
| 结果一致率（3 次的通过与否完全相同的样本比例） | 95.0% |
| 景点集合 Jaccard（同一样本不同次运行之间，平均） | 0.84 |
| Judge 分标准差（同一样本 3 次之间，平均） | 1.94 |
| 合格计划质量分 | 79.7 ± 0.7（n=101） |

- 40 个样本里有 2 个的通过与否在 3 次之间不一致，其余 38 个三次结论相同。通过率的轮间波动约 ±3 个百分点，所以主结果里单次运行 1–2 条样本的差异不能当作结论。
- 同一样本的行程每次大约 84% 的景点相同，Judge 分的轮内波动（约 2 分）和 full 与 baseline_catalog 的质量分差距（2.9 分）在同一量级，那个差距的置信区间是在“每个样本只评一次”的前提下算的，Judge 自身的随机性没有计入。

## 对比系统

| 系统 | 说明 |
|---|---|
| `full` | 完整图；自动选择默认候选代替人工挑选 |
| `no_revision` | 照常校验，但不回退重排 |
| `baseline_catalog` | 单次生成：原始请求 + 目的地城市的完整目录 → 完整行程。只调用一次模型，不调用工具、不做规则校验、不回退 |
| `baseline` | （默认不跑，可用 `--systems` 指定）单次生成，不给目录，只能凭记忆写店名 |
| `no_memory` | 关闭长期记忆。单次会话的数据集测不出记忆的作用，所以单独用两次会话的场景评测，见下文 |

**为什么去掉 `baseline`、改用 `baseline_catalog`**
- `baseline` 看不到目录，只能凭记忆写店名。目录每个城市只收录了约 40 家餐厅、30 家酒店，模型写的店即使真实存在，也大多不在目录里，评测无法核验。所以它的硬约束通过率 0% 在运行之前就注定了（Gemini dev 全量里 60 条全部触发 `unknown_ref`），“实体幻觉率”52% 实际上是“无法在目录中核验的比例”，里面有很多真实存在的店，不能称为幻觉。full 和它的差距说明不了架构的价值。
- 要回答的问题是：**同样的数据，拆成多步并加上校验回退，比一次生成强多少？** `baseline_catalog` 拿到和 full 相同的数据：目的地城市的全部酒店、餐厅、景点，字段和 Research 返回给 full 的一致（id、名称、价格、评分、饮食标签、开放时间、区域等）。Prompt（`BASELINE_CATALOG_SYSTEM`）的规则和 Itinerary 节点一致：只能用目录条目、ref_id 填 id、开放时间、不重叠、安排午餐晚餐、饮食限制、优先必去景点、尽量不超预算。区别只是一次生成全部天数、自己选酒店、自己从原始请求里理解需求；没有加 full 没有的提示。推理强度等模型参数和其他系统相同。花费照常由评测按目录价格重新核算。
- **取舍一：目的地用标准答案**。目录要按城市给，所以直接用 gold 的目的地选目录，相当于把“目的地”这一个字段告诉了它。full 的目的地抽取准确率接近 100%，影响可以忽略。其余信息（日期、天数、人数、预算、饮食、必去景点、偏好）都必须由模型自己从请求文本里读出来，不从标准答案传入。
- **取舍二：不提供天气**。full 在知道日期之后查天气；要给 baseline_catalog 天气就得先把出行日期告诉它，而日期正是它应该自己读出来的字段。天气只影响“下雨优先室内”这一条软偏好，不参与任何硬约束判定。
- 抽取准确率、不可行识别率对它记为 n/a（它没有单独的抽取和可行性判断步骤）。

## LLM-as-Judge

- 模型只给三个子分和理由；**加权在代码里做**，权重明确、有版本记录，可以校准。
- 评分标准里给出锚点示例，用来稳定打分尺度；硬约束交给规则检查，Judge 不重复评判，只把违规列表作为参考。
- **只给硬约束全部通过的计划打分**，其余计划的 `judge` 记为空：
  - 原因：不合格计划的“质量”没有可比性。Judge 只读行程文本，分不出景点是不是编造的、日期对不对、预算超没超；单次生成、不给目录的 baseline 会写出很多真实存在但不在目录里的名店名胜，读起来很“丰富”，在 Gemini 试跑里它的 Judge 分（82.3）反而高于完整系统（79.0），尽管它没有一条计划合格。“合不合格”由硬约束通过率回答，Judge 只回答“合格的计划里谁更好”。
  - 好处：不合格的计划不调用 Judge，省下这部分费用。
  - 用 `rejudge` 重新打分时也遵守这条规则，并先用当前的评测规则重算一遍是否合格（`--rules-only` 只重算规则、不调用 Judge）。
- **系统之间比较质量分用配对子集**：只取两个系统都通过的同一批样本（同一样本、同一轮）比较，报告里有单独的“配对比较”表，`eval-compare` 比较两次运行时也一样。直接比各自的平均分有选择偏差：较弱的系统（如 `no_revision`）往往只在简单样本上通过，简单样本的计划分数本来就高，平均分会虚高。
- **校准用的人工标注也只从合格计划里抽**：`calibrate <run> human.csv --make-template 30` 按“系统 × 难度”分层，从硬约束通过、已有 Judge 分的计划里抽样生成待标注表；校准时不合格计划上的标注会被忽略并计数。
- Judge 最好换一家模型或用更强的一档，避免模型偏向自己生成的结果。
- **权重校准**：先用 `--make-template 30` 生成待标注表，自己给这些合格行程打总分（0–100），然后运行 `python -m trip_agents.evals.calibrate <run> human.csv`。它会在权重单纯形上网格搜索、最大化 Spearman 相关，并输出默认权重的相关系数作为对照。
- **校准结果**：项目作者已对合格计划做过人工打分校准，拟合出的权重与默认的 0.3 / 0.4 / 0.3 接近，所以沿用默认权重。

### 记忆消融（两次会话）

运行 `make eval-memory`（mock）或 `python -m trip_agents.evals.memory_eval --provider gemini --name <run>`（真实模型），脚本是 `trip_agents.evals.memory_eval`，共 40 个场景，分四类，每类 10 个：
- **inherit**：第二次会话只说城市、日期和天数，其余偏好和预算习惯应该从记忆中沿用（预算 = 每人每天 × 人数 × 新天数）；
- **override**：第二次会话明确说出不同的节奏，并说“什么都吃”，应该以新说的为准，其余照常沿用；
- **past_trip**：第二次会话说“像上次 X 那样”，应该从历史行程中取出目的地、天数、人数和预算，只换日期；
- **add_restriction**：第二次会话**新增**一项饮食限制（“这次有人海鲜过敏”），标准答案是新旧限制的并集（用户没有撤销旧的）。

两次会话的请求文本都是**模板生成的**，和主评测集一样。第二次会话的抽取结果和标准答案逐字段比较；另外统计记忆错误的两个方向：override 里旧值残留（放宽了的限制还在：行程过于保守），add_restriction 里漏掉新限制（危险：可能给过敏的人安排不能吃的东西）和丢掉旧限制。没有记忆的条件下第一次会话不跑（没有记忆存储、也不是同一个会话，影响不到第二次）。这里不用 Judge：要回答的是“该带过来的有没有带过来”，用逐字段比对就能判定；没有记忆的一侧基本没有行程可评。

**真实模型结果（`gemini_memory_v1`，Gemini 3.8 Flash，推理强度 low，40 个场景，花费 $2.57，报告见 [`evals/results/gemini_memory_v1/report.md`](../evals/results/gemini_memory_v1/report.md)）**：

| 场景 | 有记忆：字段全对 | 有记忆：硬约束通过 | 无记忆：能否直接规划 |
|---|---|---|---|
| inherit | 60% | 100% | 0% |
| override | 40% | 100% | 0% |
| past_trip | **100%** | 100% | 0% |
| add_restriction | **0%** | 10% | 0% |

| 字段级错误数（有记忆，每类 10 个） | 人数 | 预算 | 饮食限制 | 其他字段 |
|---|---|---|---|---|
| inherit | 4 | 4 | 0 | 0 |
| override | 6 | 6 | 0 | 0 |
| past_trip | 0 | 0 | 0 | 0 |
| add_restriction | 4 | 4 | 10 | 0 |

- **override 没有旧记忆残留**：旧饮食限制残留 0/10，旧节奏残留 0/10，用户这次说的都覆盖了记忆。
- **add_restriction：新限制从不漏（0/10），但记忆里的旧限制 10/10 被丢掉**。原因在记忆合并（`memory/ops.py` 的 `apply_memory_defaults`）：它按字段整体替换，这次只要说了任何饮食限制，就不再用画像里的饮食限制。“不吃辣”的用户说“这次有人海鲜过敏”，系统只避开海鲜。mock 下结果相同（10/10），说明是合并规则的问题，不是模型的问题。修法是饮食限制这类安全相关的列表字段取并集、只有“什么都吃”才清空；主流程代码目前冻结，没有修改。
- **人数和预算总是一起错（30 个需要沿用人数的场景里错 14 个，全部是 2–3 人被当成 1 人）**，past_trip 不受影响（人数直接取自历史行程）。原因（根据代码路径推断，Gemini 写进画像的原文没有保存，未直接验证）：画像只把同行人存成自由文本 `companions`（如“女朋友”“家人（3人）”），再由 `companions_to_travelers` 解析回人数，只认识“N人”、“独自”和情侣类说法；解析不出时人数为空，而 `RequestExtraction.to_request` 会把空人数**默认成 1**，不追问。预算按人数换算，所以跟着错。mock 写入的同行人格式恰好能被解析，所以 mock 全对。修法：画像里直接存人数，不能确定时追问而不是默认 1。
- **无记忆**：四类场景都缺预算或人数，自动模式下 0% 能直接规划（实际使用中会转为追问用户），这一列在跑之前就已知，只作参照。

mock 结果见 [`mock_memory.md`](eval/mock_memory.md)；mock 的偏好写入和读取用的是同一套规则，只能验证记忆读写和优先级逻辑。
