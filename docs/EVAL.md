# 评测方法

一条命令跑完：

```bash
make eval ARGS="--split dev --repeats 3"          # 默认 mock，无需 key
```

产物在 `evals/runs/<name>/`：`meta.json`（模型、commit、数据集、种子）、`records.jsonl`（每条样本 × 系统 × 第几次运行的明细）、`summary.json`、`report.md`。用同一个 `--name` 重跑时会跳过已完成的记录，可以断点续跑。比较两次运行：

```bash
make eval-compare A=evals/runs/<a> B=evals/runs/<b>
```

## 数据集

`evals/datasets/{dev,test}.jsonl`，由 `python -m trip_agents.evals.dataset` 生成（seed=42，共 200 条，dev 60 / test 140）。

1. **先采样结构化约束，再改写成自然语言。** 每条样本保存生成它的约束（`gold`），用作标准答案。改写有两种方式：`template` 是确定性模板，mock 抽取器能 100% 还原；`llm` 是让模型改写，更口语化，需要 key，会产生费用。
2. **难度在生成时确定**（简单 35% / 中等 40% / 困难 25%），看约束数量和预算松紧，与模型表现无关：

   | 难度 | 天数 | 人数 | 饮食限制 | 必去景点 | 兴趣 | 预算 / 典型花费 |
   |---|---|---|---|---|---|---|
   | 简单 | 1–3 | 1–2 | 0 | 0 | 0–1 | 1.6–2.2× |
   | 中等 | 2–4 | 1–3 | 0–1 | 0–1 | 1–2 | 1.15–1.5× |
   | 困难 | 3–5 | 2–4 | 1–2 | 1–2 | 2–3 | 0.85–1.05× |

3. **不可行样本**（约 6%，12 条）：预算是“全目录最低可行花费”的 0.4–0.7 倍。这个下界用整个城市目录计算，公式与 Budget Agent 相同。可行样本的预算至少是下界的 1.25 倍。
4. **期望工具**：天气、景点、餐厅三类必查；多日行程再加酒店和路线。
5. **划分**：按难度 × 可行性分层；test 集只用于最终评测。

## 评判：不相信系统的自我报告

系统内部用**自己检索到的结果**做校验。评测时，最终行程会重新对照**完整城市目录**和**标准答案约束**检查一遍（`evals/world.py`）：

- 引用既可以是 id，也可以是名称（没有检索的系统只知道名称），先统一解析成 id；解析不了的算作**实体幻觉**。
- 用的是标准答案里的约束，而不是系统抽取出来的。因此抽取错误也会体现在结果里。

## 指标

| 类别 | 指标 | 定义 |
|---|---|---|
| 结果 | 结构正确率 | 天数正确且每天至少有一项活动 |
| | 硬约束通过率 | **只统计可行样本**：日期、时间冲突、开放时间、引用、饮食、必去景点、预算全部通过 |
| | 实体幻觉率 | 无法解析的引用数 ÷ 引用总数 |
| | 需求抽取准确率 | 7 个硬约束字段的平均准确率 |
| | 不可行识别率 / 误报率 | 不可行样本中被标记出来的比例 / 可行样本中被误标的比例 |
| | Judge 分 | 丰富度、偏好符合度、合理性三个维度（各 0–100），由代码加权（默认 0.3 / 0.4 / 0.3） |
| 过程 | 工具精确率 / 召回率 | 实际用到的工具集合与期望工具集合比较，按样本取平均 |
| | 无效调用率 / 重复调用率 | 汇总所有调用后计算 |
| | 步数、回退次数、解析失败次数 | 取平均 |
| 效率 | token、估算费用、端到端耗时的均值和 P95、各节点耗时 | 单价表里没有的模型，费用显示为 n/a，不做估算 |
| 稳定性 | 结果一致率、景点集合 Jaccard、Judge 分标准差 | 同一样本多次运行之间比较，需要 `--repeats ≥ 2` |

多次运行时，每个指标先按每一轮算出来，再报告各轮的**均值 ± 标准差**。每轮的种子是 `seed + rep`；目前只有 OpenAI 支持传入 seed。

## 对比系统

| 系统 | 说明 |
|---|---|
| `full` | 完整图；自动选择默认候选代替人工挑选 |
| `no_revision` | 照常校验，但不回退重排 |
| `no_research` | 不调用任何工具，Agent 凭模型自身知识规划 |
| `baseline` | 单次生成：原始请求 → 完整行程，没有检索、校验和重试 |
| `no_memory` | 关闭长期记忆。单次会话的数据集测不出记忆的作用，所以单独用两次会话的场景评测，见下文 |

## LLM-as-Judge

- 模型只给三个子分和理由；**加权在代码里做**，权重明确、有版本记录，可以校准。
- 评分标准里给出锚点示例，用来稳定打分尺度；硬约束交给规则检查，Judge 不重复评判，只把违规列表作为参考。
- Judge 最好换一家模型或用更强的一档，避免模型偏向自己生成的结果。
- **权重校准**：自己给大约 30 个行程打总分，存成 CSV，然后运行 `python -m trip_agents.evals.calibrate <run> human.csv`。它会在权重单纯形上网格搜索、最大化 Spearman 相关，并输出默认权重的相关系数作为对照。

### Mock 模式（只验证流程，不代表质量）

- [`mock_dev_before_fix.md`](eval/mock_dev_before_fix.md)：commit `c23e7a4`，dev 60 条 × 3 次，2026-11-02
- [`mock_dev_after_fix.md`](eval/mock_dev_after_fix.md)：commit `ae92992`，同样的配置
- [`mock_dev_compare.md`](eval/mock_dev_compare.md)：前后对比

mock 模型是确定性的，所以稳定性恒为 1，标准差恒为 0。mock 规划器本身不会出错，所以 `full` 和 `no_revision` 的差距只能说明回退链路是通的，不能说明真实模型会出多少错。

**这次评测发现的问题**（dev 集）：修复前，`full` 系统的失败全部是超预算。原因是用户要高档酒店但预算有限时，Research 只检索该档次的酒店：一方面“最低可行花费”被高估，导致 7% 的可行样本被误判为不可行；另一方面回退只能重排每天的行程，换不了酒店。修复方式：预算优先于住宿档次偏好，按限价补查酒店；回退时允许换成更便宜的酒店，并告知用户。修复后，可行样本的硬约束通过率从 84.2% 提升到 100%，误报率从 7.0% 降到 0%（mock，dev 60 × 3）。

### 记忆消融（两次会话）

运行 `make eval-memory`，脚本是 `trip_agents.evals.memory_eval`，共 30 个场景，分三类：
- **inherit**：第二次会话只说城市、日期和天数，其余偏好和预算习惯应该从记忆中沿用；
- **override**：第二次会话明确说出不同的节奏，并说“什么都吃”，应该以新说的为准；
- **past_trip**：第二次会话说“像上次 X 那样”，应该从历史行程中取出目的地、天数、人数和预算。

第二次会话的结果和标准答案逐字段比较。结果见 [`mock_memory.md`](eval/mock_memory.md)（mock）。mock 的偏好写入和读取用的是同一套规则，所以准确率由构造决定，只能验证记忆读写和优先级逻辑。
